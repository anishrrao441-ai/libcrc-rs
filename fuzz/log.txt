HOW THE TWO SIDES ARE COMPARED
  Shared public API. Both sides are handed identical bytes and asked for all 13
  exported entry points, plus the same twelve values rebuilt one byte at a time
  through the 8 update_crc_* functions.

  Oracle   the ORIGINAL C libcrc, built from the pristine upstream tree with the
           project's own CFLAGS (-O3 -funsigned-char). It lives in the gitignored
           oracle/ directory and nothing in crates/ links, calls or depends on it.
  Port     crates/libcrc-rs, called directly as a Rust library. No FFI, no shim,
           no C in the measured path.

  BATCH, NOT STREAM. Each round writes a whole batch to a file, runs the oracle
  once with stdin closed, waits for it to exit, then reads the results file. No
  pipe is ever read, so the Windows anonymous-pipe deadlock that a long-lived
  bidirectional oracle would risk has no surface here. CRC is a pure function;
  there is nothing to interleave.

ORACLE SELF-CHECK (run before the clock started)
  The oracle is asked for "123456789" and its answers are compared against the
  values recorded from the upstream library in 00-VERIFIED-FACTS.md §11. If the
  oracle were mis-built — most likely by dropping -funsigned-char, which libcrc
  requires — it would be wrong itself and every 'divergence' below would be an
  artefact. Result: PASS

DIVERGENCES
  None. 1100000 cases x 25 value comparisons = 27500000 comparisons, all identical.

  Stated precisely, because the distinction matters: this is byte-for-byte
  agreement on every input the generator produced. It is evidence, not proof.
  crc_sick in particular has no external reference implementation — libcrc is
  its only definition — so its correctness argument rests entirely on this
  differential parity.

UPSTREAM NOTE — a public API that cannot be called
  Building this harness surfaced it mechanically. include/checksum.h:99 declares

      uint64_t update_crc_64_ecma( uint64_t crc, unsigned char c );

  and no definition exists anywhere in src/. `nm lib/libcrc.a | grep update_crc_64`
  reports exactly one symbol, `update_crc_64`, which the public header does NOT
  declare. So the documented incremental CRC-64 entry point fails to link, and the
  one that works is undocumented. fuzz/oracle_harness.c has to declare
  `update_crc_64` itself to reach it — that extern is the evidence. Reproduce with
  fuzz/prove_d01.sh.

WHAT THIS RUN DOES *NOT* SHOW
  - It compares crates/libcrc-rs directly. The C-ABI shim in crates/libcrc-cabi is
    covered separately, by the unmodified original test suite linking against it.
    The NULL-pointer cases here do exercise the shim's NULL->empty-slice mapping
    as a model, but not the shim's own pointer arithmetic.
  - Inputs are generated, not coverage-guided. cargo-fuzz needs a nightly
    toolchain and this machine has none, so there is no libFuzzer feedback loop
    steering toward new edges. The mitigation is the fixed corpus above, which
    pins the structural edge cases rather than hoping to stumble on them.
  - Single platform: x86-64 windows-gnu. libcrc's lazy table initialisation is
    unsynchronised, which is undefined behaviour under C11 5.1.2.4 and can go
    wrong on a weakly ordered CPU; x86 is TSO and will not show it. The port has
    no runtime initialisation at all, so it cannot exhibit the bug either way.
  - Single-threaded. Concurrency is a separate exercise, not this one.
